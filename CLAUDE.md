# CLAUDE.md: vedrí VP Toolkit

An Unreal Engine editor plugin that takes a project from blank to ready-to-shoot for virtual production:
green screen or LED, Blackmagic or AJA, Mo-Sys or FreeD tracking. Targets UE 5.5, 5.6 and the newest
5.x, Win64 only. The requirements are in `docs/BRIEF.md`; decisions and departures from the brief are in
`docs/PLAN.md`, which wins where the two disagree. Read both before starting work.

## Non-negotiable working rules

1. **Never guess an Unreal API.** Every engine class, function, property, plugin and module name must
   trace to a header you read in `../ue-ref/<version>` (sparse clone of `EpicGames/UnrealEngine`; see the
   brief, rule 1). If the clone fails, stop and tell the owner. Don't fall back to memory.
2. Anything you couldn't verify gets a `// TODO(verify-on-pc): <what and why>` comment **and** an
   entry in `docs/WINDOWS_TODO.md`. Data that needs a spec sheet (sensor sizes, panel pitch) gets
   `TODO(confirm-spec)`, listed in the same file.
3. Version differences: `#if ENGINE_MAJOR_VERSION == 5 && ENGINE_MINOR_VERSION >= N`. The comment
   names the behaviour on both sides.
4. Each milestone ends with: a review pass, with findings and fixes written in the commit message (see
   the brief, rule 5); `make -C Tests/Standalone all-compilers` green; `docs/WINDOWS_TODO.md` and
   `docs/TEST_PLAN.md` updated.
5. Small commits, each one buildable. No model names or identifiers in commits, code or docs.
6. Ask the owner before: choosing between two reasonable architectures, anything touching licensing or
   redistribution, and nDisplay generation details you aren't sure of.

## Core layer rules (`Private/Core/`)

The core holds pure logic that must be proven without an engine: wall maths, timing, preset schema and
JSON, validation, the Summary/Apply diff model, and the setup report.

- Header-only, `inline` functions, namespace `Vedri::Core`. No anonymous namespaces or `static` free
  functions in headers (unity builds). Each header includes what it uses.
- **No engine headers, no `UObject`, no exceptions, no RTTI.** It builds with `-fno-exceptions -fno-rtti`, so
  avoid anything that throws (`std::stoi`, `.at()` on bad input, `std::locale("name")`).
- **No user-facing text.** Findings are `ValidationIssue{Severity, Code, Field, Args}`. Every code is listed
  in `docs/VALIDATION_CODES.md`, and `make test` fails if one is missing. Report text comes in through
  `ReportStrings`, filled from `LOCTEXT`. Argument values are numbers, ids or names, never English
  words.
- **ASCII-only source.** Write non-ASCII as escapes: `"vedr\xC3\xAD"` in Core and tests (UTF-8 bytes),
  `TEXT("vedrí")` in editor code. Comments say "vedri" without the accent.
- Locale-independent numbers: streams are imbued with `std::locale::classic()`. Use `FormatNumber` and
  `FormatJsonNumber`.
- Watch out for macro collisions. Unreal and the Windows SDK define `PI`, `DELTA`, `check`, `verify`,
  `ensure`, `TEXT`, `near`, `far`, `small`, `interface`, `IN`, `OUT`, `ERROR`, `DELETE`, `IGNORE`,
  `TRANSPARENT`, `GetObject`, `GetMessage`, `CreateFile`, `Yield`, `RGB()`, `min()`, `max()` and others.
  `Tests/Standalone/PoisonMacros.h` defines them all as compile errors, so a clash fails here first. Add any new
  one you hit.
- C++20 (defaulted `operator==` is used). Engine-neutral units: metres, millimetres, a right-handed stage
  frame (see `VPCoreWallLayout.h`). Conversion to Unreal's frame happens in the editor or nDisplay layer.
- Every Core header has a matching `Tests/Standalone/Test<Area>.cpp`.
- Editor code never writes `using namespace Vedri::Core;`, because names like `Resolution` or `ESurface` could clash
  with engine names. Use `namespace VPCore = Vedri::Core;` and qualify.

## Naming

- Core: plain PascalCase types without Unreal prefixes (`WallSpec`, `ChangeSet`), files `VPCore<Area>.h`.
  Enums `E<Name>`, bools `b<Name>`, `In`/`Out` parameter prefixes, tabs, Allman braces (Epic style).
- Editor/runtime: Epic prefixes with `VP`: `UVPToolkitSettings`, `FVPEnablePluginsAction`,
  `SVPWizardStepTiming`, `IVPVideoIOProvider`, `FVPBlackmagicProvider`. Log category `LogVPToolkit`.
- Generated assets go under `/Game/VPToolkit/{Config,nDisplay,Blueprints,Levels,Lens}/`: `MP_VPToolkit`
  (Media Profile), `BP_VP_TrackedCineCamera`, `L_VP_GreenScreen_Stage`, `L_VP_LED_Stage`, `LF_VP_Default`.
- Change keys: `plugin:<Name>`, `setting:<Section or /Script/Class>/<Property>`, `asset:<ObjectPath>`,
  `file:<ProjectRelativePath>`. They're persisted in presets, so never rename one without a schema
  migration.

## Setup actions (`Private/Actions/`)

Each action is one class implementing `IVPSetupAction`:
`Validate(const WizardConfig&) -> IssueList`, `Preview(const WizardConfig&) -> std::vector<Change>`
(built only with `DiffSetting`, `DiffPlugin`, `DiffGenerated`), and `Apply(const ChangeSet&) ->
std::vector<ApplyResult>`, which touches only ticked items that belong to the action. The wizard only
composes actions. Rules:
- Preview never modifies anything. Apply never does anything Preview didn't report.
- Generated assets and files carry a generator fingerprint (`FingerprintJson` of the config section they
  came from). If the fingerprint matches, the item is `Unchanged`. Assets the toolkit didn't make are
  `Overwrite`, unticked by default.
- Settings go through `UDeveloperSettings` / `SaveConfig`, never hand-edited `.ini` files.
- Log every applied change to `LogVPToolkit`.
- One tracked camera for now (D4). Read tracking and lens settings through a single accessor, and name
  camera assets so a second camera fits alongside them. Multi-cam arrives as preset schema v2.

## Adding a video I/O card family

1. Write one class implementing `IVPVideoIOProvider` in `Private/IO/`. It reports: family id,
   detection (plugin enabled, devices present), the timecode provider, custom time step, media source and
   media output classes **by object path**, property setters done through reflection (every name verified
   against that plugin's headers), and the pixel formats and key+fill it supports.
2. Register it with the provider registry. The id then appears in `ValidationContext::KnownCardFamilies`.
3. Add its plugin to the Step 1 plugin table. No `.Build.cs` change (D2: no compile-time link).

## Adding a tracking source

Write one class implementing `IVPTrackingSourceProvider` in `Private/Tracking/`. It reports: id, detection,
the Live Link source to create, its settings, and which data it supplies (transform, FIZ). Register it;
the id appears in `ValidationContext::KnownTrackingSources`.

## Commands

- `make -C Tests/Standalone`: build and run the core tests (clang), then check the code catalogue.
- `make -C Tests/Standalone all-compilers`: clang and gcc. `make -C Tests/Standalone sanitize`: ASan/UBSan.
- `make -C Tests/Standalone presets`: regenerate the bundled presets from `BundledPresetDefinitions.h`.
  Never hand-edit the JSON; a test fails if it drifts.
